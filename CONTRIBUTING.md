# Contributing

Contributions that make this blueprint clearer, safer, or more useful are welcome. You do not need to know GitHub or Git to understand the documentation or suggest an improvement. You can describe a correction or question in an issue, or propose an edit if you are comfortable doing so.

By submitting original documentation, you offer that contribution under CC BY 4.0 while retaining rights in your original work. Submit original documentation only if you are able to offer it under those terms; see [LICENSE](LICENSE).

## Helpful contributions

- Explain an unclear term in plain language.
- Improve the structure or accessibility of the docs.
- Point out a safety concern or an unsupported claim.
- Suggest a provider-neutral principle or identify where an example is specific to one tool.

Please keep proposals focused. This repository is currently documentation-only; do not assume a working setup or tested procedure exists.

## Protect private information

Use synthetic data and placeholders such as `[BUSINESS_NAME]` and `[EXAMPLE_VALUE]`. Never include credentials or tokens, customer/employee/business records, personal memory or transcripts, private profiles, machine-specific paths, or real operational data in issues, docs, examples, or screenshots. Review the complete commit and diff before publishing. See [Privacy and safety](docs/privacy-and-safety.md) for data-flow and safe-use guidance.

## Pre-publish checklist

- [ ] Write in plain language and label the evidence accurately; do not imply a test or guarantee that did not happen.
- [ ] Check links and verify any cited upstream/source versions or claims; include the date checked where relevant.
- [ ] Scan the full commit and diff for credentials, private paths, personal information, real records, or identifying details; use synthetic data and placeholders.
- [ ] Review license and attribution requirements; submit original documentation under the existing [CC BY 4.0 contribution terms](LICENSE), and do not copy upstream docs or assets.

## Plain-language standard

Write so that a small-business owner unfamiliar with GitHub can follow the content. Explain unavoidable technical terms, distinguish examples from requirements, and link to authoritative upstream project pages rather than copying their documentation or configuration. See [Maintenance and support scope](docs/maintenance.md) for the lightweight review practice and the boundary between this repository and upstream support.
